## Long-term Knowledge

### Architecture

<!-- lore:019e19db-810c-7609-b053-9be113f84eb3 -->
* **Agents lack cross-session access by design**: Agents lack cross-session access by default: the SDK client (session.list/get/messages/prompt) is not exposed to agent tools. Cross-session behavior is mediated via dispatches \[\[019e19e2-9c09-7787-b48d-ca2d2685b261]]. To enable it, explicitly expose wrapper tools (e.g. lifecycle tools) that call \`client.session.\*\` via closure. Pattern: use \`store\` for discovery (entities/dispatches → session\_id), then \`client\` inside tools for direct session interaction (read/post messages). This preserves audit semantics while enabling controlled cross-session access.

<!-- lore:019e1932-c47d-79c4-8f00-171a6fbd6f01 -->
* **Concurrency limited by semaphore, not sessions**: Throughput is controlled by a global semaphore (\`max\_concurrent\`, default 2, configured in \`opentower.config.json\`) that limits parallel LLM dispatches, not total sessions. Sessions, entities, DB rows, and per-session queues are unbounded; excess events queue and batch via \`batch\_window\_ms\`. Increasing \`max\_concurrent\` raises parallel LLM load and resource usage but does not change queueing behavior.

<!-- lore:019e089b-dcc8-7d49-bb47-9b18d2b06221 -->
* **Cron scheduling lives inside opentower**: Cron scheduling is implemented inside opentower: jobs are stored in SQLite and executed via the pipeline to preserve session affinity and observability. Each run creates a cron\_executions row with delivery\_id \`cron:{jobId}:{timestamp}\`. \`run\_once\` jobs auto-disable after success. Recurring jobs enforce a ≥1h interval via shared validation (API and agent tools). There is no general delayed dispatch primitive—short delays must use \`run\_once\` jobs (e.g. polling loops), which can bypass the 1h limit but are one-off executions, not true recurring sub-hour schedules.

<!-- lore:019e0810-33aa-77ef-84d3-56e20c1fb002 -->
* **Dashboard bundled and served by opentower**: Dashboard is bundled into \`packages/opentower/public\` and served via Hono for a single-origin API+UI. \`public/\` is a build artifact (gitignored) generated in \`prepublishOnly\` and included via \`files\` when published. If missing at runtime, the UI won’t be served. The frontend assumes same-origin APIs: requests use \`new URL(path, window.location.origin)\` with endpoints like \`/api/\*\` and \`/healthz\`, with no configurable base URL. This design simplifies auth and avoids CORS but requires the server and UI to be deployed together.

<!-- lore:019f1c56-2452-79b9-bdaf-5978e44b6542 -->
* **opentower allowlist: allowed\_orgs/allowed\_repos on WebhookConfig, enforced in matchers.ts**: Allowlisting is implemented as \`allowed\_orgs?: string\[]\` and \`allowed\_repos?: string\[]\` on \`WebhookConfig\` in \`types.ts\`. Enforcement is in \`matchers.ts\` inside \`evaluateAndDispatch()\` (fail-closed). Repo scope: \`payload.repository.full\_name\` for GitHub events; \`entityKey.repo\` for email events. If no repo can be resolved and allowlist is configured, dispatch is skipped with reason \`repo\_not\_allowed\` in the existing \`skipped\[]\` response shape. \`allowed\_repos\` matches \`owner/repo\` exactly (case-insensitive); \`allowed\_orgs\` matches the owner part. Empty/missing allowlist = allow-all (default unchanged). Normalization (lowercase+trim+filter) happens in \`bootstrap.ts\` before passing into \`HandlerContext\`.

<!-- lore:019f1c56-2454-7596-858d-af43e3f6a491 -->
* **opentower MCP endpoint: @hono/mcp + @modelcontextprotocol/sdk v1.x on existing Hono server**: MCP endpoint lives in \`packages/opentower\` only. Uses \`@hono/mcp@0.3.0\` (peer: \`@modelcontextprotocol/sdk ^1.25.1\`) with \`StreamableHTTPTransport\` + \`transport.handleRequest(c)\` on \`app.all('/mcp', …)\`. Reuses \`createBearerAuth\` factory (same \`safeTokenCompare\` as \`/api/\*\`). Validates \`Origin\` per MCP spec — localhost/no-Origin requests exempt; \`\*\` CORS allows all; otherwise must match \`OPENTOWER\_CORS\_ORIGIN\`. MCP endpoint only mounted when \`OPENTOWER\_API\_TOKEN\` is set; warns if not set. Exposes \`start\_agent\_session\` tool calling \`pipeline.dispatch\`/\`dispatchNoAffinity\`. Stateless mode: \`Mcp-Session-Id\` header is NOT issued by \`@hono/mcp\` StreamableHTTPTransport in stateless mode — expected behavior. Session termination: HTTP DELETE with \`Mcp-Session-Id\` header. mathuraditya724 is the author of \`@hono/mcp\`.

<!-- lore:019f0f06-0dbf-76f8-8194-69419f9ab79d -->
* **outpost CI/publish workflow split: ci.yml builds image, publish.yml deploys**: MathurAditya724/outpost uses a two-workflow release model: \`ci.yml\` runs on push to \`main\`/\`release/\*\*\` — builds and pushes Docker image tagged with commit SHA to ghcr.io (permissions: \`contents: read\`, \`packages: write\`). \`publish.yml\` triggers on issue labeled \`accepted\` — waits for CI on the release branch, then runs \`craft publish\` using a GitHub App token. \`release.yml\` is triggered manually via \`workflow\_dispatch\` and runs \`craft prepare\`. This separation means the publish step depends on CI completing successfully on the release branch.

<!-- lore:019f11da-814b-7445-8268-745424f4b2a1 -->
* **outpost Dockerfile: port exposure and Railway deployment**: Dockerfile exposes ports 4096 (OpenCode web UI) and 5050 (opentower webhook server). CMD binds OpenCode to \`0.0.0.0:${PORT:-4096}\`, so Railway's injected \`PORT\` env var is picked up automatically. The \`docker-entrypoint.sh\` handles: volume permissions, git init in \`~/dev\`, GH identity setup via \`gh api user\` (falls back to \`developer@outpost.local\`), then execs the CMD. The \`xdg-open\` ENOENT error in headless containers is harmless — Linux desktop URL-opener absent, not a Railway connectivity issue. opentower's webhook port (5050) is separate from OpenCode's web port and must be independently reachable if webhooks are needed.

<!-- lore:019e083b-79b8-7072-9aac-fdc266d848cb -->
* **Plugin self-hosts HTTP server via Bun.serve**: The opentower plugin does not integrate into an existing OpenCode HTTP server; it starts its own standalone server using \`Bun.serve()\` (default port 5050). OpenCode only loads the plugin function for side effects. This means routing, static serving, and API endpoints are entirely owned by the plugin process, not OpenCode.

<!-- lore:019e089b-dcdd-744a-8a8e-be49b2affdce -->
* **Proxy Cloudflare worker APIs through opentower**: Expose Cloudflare email-worker data (e.g. allowed\_senders) via opentower API instead of calling the worker directly from the dashboard. Add proxy routes in opentower that forward to the worker using the same API token/secret. This maintains the single-origin model, avoids leaking worker URLs to the client, and keeps auth consistent with OPENTOWER\_API\_TOKEN.

<!-- lore:019e0810-33b8-788e-aa05-b1ccff7abd46 -->
* **Removed multi-server support in dashboard**: Dashboard no longer manages multiple servers. All server config (URL, token, opencodeUrl) and related hooks (\`use-servers\`, schemas, server CRUD UI) were removed. The app now assumes a single backend (same origin) and only handles a single auth token.

### Gotcha

<!-- lore:019e049d-8b73-737f-9827-63d19abac7aa -->
* **@loreai/opencode 0.13.0–0.13.3 unusable in bun workspaces due to fastembed workspace deps**: \`@loreai/opencode\` versions 0.13.0–0.13.3 and \`@loreai/core\` 0.13.3 transitively depend on \`fastembed@^2.1.0\`, which declared unresolvable \`workspace:\*\` deps (\`gearhash-jit\`, \`@huggingface/blake3-jit\`). Bun failed with "Workspace dependency not found" during install. This was resolved in 0.13.4 — \`fastembed@2.1.0\` on npm no longer carries the broken workspace deps. Note: bun's registry cache may lag npm by minutes — a version appearing in \`npm view ... versions\` may not resolve immediately in bun.

<!-- lore:019e0124-c974-7caf-8f4d-3c25402415c4 -->
* **Biome expects 2-space indentation; tabs cause CI failure**: Biome must ignore generated assets. The repo enforces 2-space indentation, but bundled/minified files (e.g. \`packages/opentower/public\`) will fail linting. Fix: add \`public\` (and similar build output dirs) to \`biome.json.files.ignore\`. Otherwise CI fails on style rules against compiled code.

<!-- lore:019e1458-eaa2-7883-b504-e23b488bd7ae -->
* **bun pm pack skips prepublishOnly (missing public/)**: \`public/\` inclusion depends on install method: npm installs include it via \`files\`, but \`file:\` deps do not. When \`opentower\` is used as \`"file:./packages/opentower"\`, Bun uses the raw source directory, bypassing \`files\` and \`prepublishOnly\`, so \`public/\` (gitignored) is missing. Docker builds must explicitly build and copy the dashboard into \`public/\`. This is why Docker cannot rely on npm packaging behavior when using local file deps.

<!-- lore:019e0121-de4a-758d-bd3f-baeb2ab25110 -->
* **bun.lock goes stale when adding packages inside a workspace subdirectory**: Running \`bun add\` inside a workspace package (e.g. \`packages/dashboard\`) updates that package's local state but may not update the root \`bun.lock\`. CI uses \`bun install --frozen-lockfile\` at the repo root, so a stale root lockfile causes build failure with "lockfile had changes, but lockfile is frozen". Fix: always run \`bun install\` from the repo root after adding any dependency, then commit the updated \`bun.lock\`.

<!-- lore:019e145e-dd3d-7e38-9e90-5cf1c88c4ac3 -->
* **Craft publish expects prebuilt GHCR image by commit SHA**: Craft publish requires a GHCR image tagged with the commit SHA; if CI hasn't built/pushed it, publish fails with 'ghcr.io/...:\<sha>: not found'. Fix: wait for CI on the release branch before publish (e.g. \`gh run watch\`). Guard against empty/null results from \`gh run list\` — fail fast if no run exists. In MathurAditya724/outpost, the publish.yml workflow handles this wait explicitly before calling \`craft publish\`. Also: craft@v2 creates a release branch and pushes it before the publish step — if the run fails mid-way, the release branch may already exist on remote. Additional gotcha: GHCR \`write\_package\` denied even with \`packages: write\` declared. Trap: workflow permissions + repo settings look sufficient. Real fix: GHCR has independent access control — visit https://github.com/users/MathurAditya724/packages/container/outpost/settings → 'Manage Actions access' → add the \`outpost\` repository with Write role (or enable 'Inherit access from source repository'). Setting repo workflow permissions to read/write is NOT sufficient alone.

<!-- lore:019f0f06-0dbe-7211-beb3-40104bb4a9c5 -->
* **craft@v2 publish-request requires GitHub Issues enabled on repo**: Trap: craft@v2 creates a publish-request by opening a GitHub issue (\`gh issue create -R "$PUBLISH\_REPO"\`). If Issues are disabled on the repo, this fails with 'the repository has disabled issues' → exit code 1. Looks like a permissions or token problem. Fix: enable Issues in GitHub Settings → General → Features. Also affects the earlier release-blocker check (\`gh issue list -l release-blocker\`), which is non-fatal. Applies to MathurAditya724/outpost.

<!-- lore:019e087c-ae36-7bd7-80c2-7203d286eba7 -->
* **Dashboard build fails without installing dashboard deps**: Running \`bun run build:dashboard\` from the opentower package can fail with missing types/plugins (vite, @vitejs/plugin-react, @tailwindcss/vite) if the dashboard workspace deps aren’t installed. The build script assumes \`packages/dashboard\` already has its node\_modules. Fix: run \`bun install\` at repo root (or in the dashboard dir) before building, then rerun the build.

<!-- lore:019e1421-2194-7fdc-a38a-447800384be8 -->
* **Dispatch records can exist without sessions**: Dispatch rows are inserted with \`session\_id: null\` before session creation. If \`client.session.create()\` fails or times out, they remain without sessions. Additionally, cron jobs may call \`pipeline.dispatch()\` without \`await\`, allowing the cron execution to complete before the session is created—producing dispatches that appear finished but still lack a \`session\_id\`. Check for async gaps in cron execution flow.

<!-- lore:019f13e2-8e5f-7baa-8e13-d3db9486acf4 -->
* **Email webhook URL should target /webhooks/email**: Trap: \`WEBHOOK\_URL\` looks like it should include the service port (\`:5050\`) because opentower listens there. Fix: use \`https://agent.maditya.sh/webhooks/email\` when the domain is already routed to opentower; only add \`:5050\` if that port is publicly exposed directly. The wrong URL seems right because the webhook server does run on 5050, but the worker should target the externally reachable base path, not the internal listener port.

<!-- lore:019e00de-f555-75cf-90a0-b08a79b4474b -->
* **Hono middleware registration order: /healthz bypasses app.use('\*') registered after it**: Hono middleware order matters: middleware only applies to routes registered after it. If \`/healthz\` is defined before \`app.use('\*', ...)\`, it bypasses global middleware like CORS. Fix: register \`app.use('\*', cors({...}))\` as the very first call on the app, before any routes or \`app.onError\`. Also ensure CORS is not scoped only to \`/api/\*\` if endpoints like \`/healthz\` must be browser-accessible, and include required methods (e.g. POST) for webhook preflight.

<!-- lore:019f1c70-3d25-7ef7-8e89-ce196e8d4abe -->
* **opencode-cloudflare-email-worker has pre-existing TS2345 error unrelated to opentower changes**: Trap: \`bun run --filter '\*' typecheck\` fails with TS2345 in \`packages/opencode-cloudflare-email-worker/src/index.ts:69:46\` (\`{ fatal: false }\` not assignable to \`TextDecoderConstructorOptions\` — missing \`ignoreBOM\`). Looks like a regression from current changes. Fix: verify via \`git stash\` + checkout \`main\` — error exists on \`main\` and is pre-existing, unrelated to any opentower work. Do not attempt to fix it as part of opentower feature branches.

<!-- lore:019e1434-aad7-7b0f-b957-3ced873e8384 -->
* **opencode-config-bun.lock must be regenerated via temp install**: \`opencode-config-bun.lock\` is validated in CI by regenerating it via an isolated temp install and diffing. Rebases or merges can leave stale entries (e.g. removed deps like \`typescript\`) that cause CI failure even if builds pass locally. Do not edit or merge manually—always regenerate using the temp-install method from \`opencode-config-package.json\` and commit the result.

### Pattern

<!-- lore:019e1a14-cfc4-72f4-b090-9f919c8fc8db -->
* **Centralize SDK error extraction with helper**: Avoid inline casting of SDK errors (e.g. \`(err as { data?: { message?: string } })...\`). Instead, use a small helper (e.g. \`errorMessage(err, fallback)\`) to safely extract \`data.message\`. This reduces repetition, simplifies call sites, and avoids brittle type assertions across tools.

<!-- lore:019f14da-351c-7908-b91f-845fc6f76620 -->
* **Cloudflare Email Worker: verbatim forward vs. webhook payload**: The Cloudflare Email Worker has two distinct behaviors: (1) When \`FORWARD\_TO\` is set, it forwards the email verbatim (full message) to that address. (2) When POSTing to the opentower plugin webhook, it sends only email headers — never the email body. These are separate code paths; do not conflate them.

<!-- lore:019e19e2-9c09-7787-b48d-ca2d2685b261 -->
* **Dispatches are canonical for opentower sessions**: Dispatches are the source of truth for opentower sessions. Do not use \`client.session.\*\` to reason about activity—they include all OpenCode sessions and bypass pipeline features. Use \`store.listDispatches()\` and related store queries for session discovery, entity context, trigger state, and observability. \`client.session.prompt()\` sends messages directly to a session without creating a dispatch, so it skips audit trails, trigger evaluation, and consistency guarantees—only use it for simple nudges. Pattern: use \`store\` for opentower concepts (dispatches, entities, triggers) and \`client\` only for session internals (messages, prompting) once you already have a \`session\_id\`. This separation avoids abstraction leaks and ensures correct session tracking.

<!-- lore:019e1421-2199-7338-8969-7a3c458f2ab3 -->
* **Email events only create dispatches if a trigger matches**: Email webhook handling calls \`evaluateAndDispatch\`, which first filters triggers via \`findMatching\`. If no trigger matches an event like \`email.ci\_activity\`, nothing is dispatched and no dispatch record is created—only a log entry (\`trigger.no\_match\`). Dispatch creation only happens inside pipeline.dispatch/dispatchNoAffinity for matched triggers.

<!-- lore:019e08d5-9a21-7b16-a10e-f018b1f867b5 -->
* **OpenCode base URL stored in localStorage**: The dashboard stores a user-provided OpenCode base URL (e.g. separate instance) in localStorage alongside the API token. This value is used only for constructing session links, not API requests. Pattern: keep API client same-origin, but allow UI-level overrides for external navigation targets.

<!-- lore:019f1c56-2457-7fe5-bcc0-5ae4be77c9e5 -->
* **opentower agent (jared): always load repo-setup skill first**: Agent \`jared\` (\`agents/jared.md\`) must always load the \`repo-setup\` skill first to prepare the worktree before any other skill. Skill load order: (1) \`repo-setup\`, (2) situation skill (\`resolve-issue\`, \`review-pr\`, \`fix-ci\`, \`respond-to-comment\`), (3) utility skills as needed. Constraints: never \`git reset --hard\` or \`git clean -fd\` in the main clone (other worktrees share objects); never push to or force-push the default branch.

<!-- lore:019f1c56-2455-7550-81e3-5b0c0242cef1 -->
* **opentower config: event field always normalized to array; allowed\_orgs/allowed\_repos always arrays**: In \`packages/opentower/src/config.ts\`, \`trigger.event\` is always normalized to an array so matchers can stay simple (no \`string | string\[]\` branching). Similarly, \`allowed\_orgs\` and \`allowed\_repos\` on \`WebhookConfig\` are normalized to arrays at config-load time (lowercased + trimmed + filtered). \`allowed\_orgs\`/\`allowed\_repos\` are also stored on \`WebhookConfig\` in \`types.ts\` and enforced in \`matchers.ts\` \`evaluateAndDispatch()\` (fail-closed). This is a repeated directive — never leave these as raw string scalars in matcher code.

<!-- lore:019f11da-814f-7bf2-bd84-e8f8ca055f77 -->
* **opentower config: no port field, uses WebhookConfig.port optional**: In MathurAditya724/outpost, \`opentower.config.json\` has no \`port\` field — the \`WebhookConfig\` type defines \`port?: number\` as optional. The running config uses \`max\_concurrent: 5\`, \`timeout\_ms: 1800000\`, and 5 triggers all routing to agent \`"jared"\`. Default opentower port is 5050 (hardcoded in plugin via \`Bun.serve()\`). To override, set \`port\` in the config's webhook section.

<!-- lore:019f1c70-3d23-70ba-a923-8d7a42e4ae1b -->
* **opentower handler.ts: createBearerAuth factory reused for /api/\* and /mcp**: Auth middleware in \`handler.ts\` is extracted as \`createBearerAuth(apiToken, label)\` — returns 503 when unconfigured, 401 on bad token. Reused for both \`/api/\*\` and \`/mcp\` routes. Trap: duplicating inline auth logic for each route looks simpler but diverges over time. Fix: always use the factory. \`safeTokenCompare()\` uses HMAC-sha256 with static key \`"opentower-token-compare"\` to normalize inputs to fixed-length digests before \`timingSafeEqual\` — constant-time regardless of input length. The static key is intentional: it only normalizes length, not for cryptographic secrecy.

<!-- lore:019f1c56-2456-785a-afcc-4f30fdfac9d5 -->
* **opentower pruneOlderThan: never deletes in-flight dispatches/executions**: \`pruneOlderThan(days)\` in \`storage.ts\` deletes only \*completed\* dispatches and cron executions not in \`pending\` or \`running\` state. In-flight rows are never deleted. This is an explicit user directive: 'never delete in-flight ones.' Orphaned links and entities with no remaining dispatches are cleaned up after.

<!-- lore:019e1417-a614-74a7-a9c1-c725f90afd26 -->
* **Plugins can register in-process agent tools**: Plugins expose agent tools via the \`tool\` hook using \`tool()\` from \`@opencode-ai/plugin\`, with zod args and async \`execute(args, context)\`. Tools run in-process and should prefer direct access to internal components (e.g. \`store\`, \`pipeline\`, \`scheduler\`) via closure rather than calling HTTP APIs or using API tokens. This avoids unnecessary network layers and ensures full access to internal state.

<!-- lore:019e1a14-6073-7ee2-9774-b22b81e14464 -->
* **Propagate ToolContext.abort to SDK calls**: Agent tools should accept the \`context\` parameter and pass \`context.abort\` to SDK calls (e.g. \`client.session.prompt/messages({ ..., signal: context.abort })\`). Without this, long-running requests continue after the invoking session is aborted, causing wasted work and inconsistent lifecycle behavior. Many existing tools omit this for simplicity, but for any network/LLM call, propagating the abort signal is the correct pattern.

<!-- lore:019e0810-33b4-77b5-a1b6-6e02e182386a -->
* **Token state via localStorage + useSyncExternalStore**: Auth token is stored in \`localStorage\` (\`opentower-token\`) and exposed via a custom store using \`useSyncExternalStore\`. \`emitTokenChange()\` manually notifies subscribers after mutations (set/clear). This avoids React context and keeps token access global and reactive across components.

<!-- lore:019e143f-9939-7f1a-bd66-58b2e96e014f -->
* **Verify email-resolved entities via gh CLI**: AI-based email entity resolution must be verified with \`gh\` CLI before dispatch. The resolver may misclassify kind (issue vs PR), breaking session affinity and link extraction. Pattern: after AI extracts \`{repo, number}\`, call \`gh pr view\` then \`gh issue view\` to confirm existence and canonical kind, and fetch the PR body for linked issue parsing. Fall back to AI-only if verification fails. This ensures correct session reuse and avoids split sessions from wrong entity types.

### Preference

<!-- lore:019f1d09-ec45-7d4b-9329-d8c8beb06a33 -->
* **Always encode agent behavioral rules directly in the agent prompt file**: When the user wants to change how an agent behaves (e.g., when to respond, what to load first, what to never do), they direct changes to the agent's prompt file (e.g., \`agents/jared.md\`) rather than relying on external config or runtime logic. Rules are written as explicit, imperative statements in the prompt (e.g., 'Always load repo-setup first', 'Never push to default branch', 'Only respond when a reply adds value'). The assistant should update the relevant agent \`.md\` file with clearly worded rule sections, commit the change to the current feature branch, and push it.

<!-- lore:019f13e0-a28c-71de-86f6-a2fa1cd8ee35 -->
* **Always inspect repository structure and relevant config before answering**: When the user asks about ports, endpoints, workflows, release behavior, or CI failures, they consistently want a full repo survey first: read the root structure, package.json, and the key config/workflow files before drawing conclusions. They also expect the answer to be grounded in exact file contents and to trace the relevant path through Dockerfiles, entrypoints, workflow YAML, and app config rather than guessing. Follow this by locating the specific setting or route, then explain the result with precise file references and any implications for deployment or CI.

<!-- lore:019f17d7-f044-77fc-ac45-a7a617225d2e -->
* **Always match documentation to official/external platform template formats exactly**: When creating or revising documentation for external platforms (e.g., Railway Marketplace), the user expects strict adherence to that platform's official template format — specific sections, approximate word counts, and structure. If an initial draft is too long or uses the wrong structure, the user will request a rewrite to match the canonical format. Always research or confirm the target platform's template requirements before drafting, and keep content concise and section-compliant rather than comprehensive.

<!-- lore:019f1c5d-0292-7247-b7e7-f88e6ecb7b89 -->
* **Always read and understand existing code structure before planning or implementing changes**: Before making any changes or writing implementation plans, the user consistently directs the agent to read all relevant source files (handlers, config, types, entry points, Dockerfiles, etc.) to build a complete picture of the codebase. This applies even when the user has already stated requirements — the agent is expected to inspect actual file contents, not rely on assumptions. The user also expects the agent to stay in a read-only/plan mode during this discovery phase and only proceed to edits after the full structure is understood. Always read the relevant files first, then plan or implement.

<!-- lore:019f1d0f-30d1-72c6-ade9-55593ce68530 -->
* **Always review then squash-merge PRs when work is complete**: When a feature branch is finished and pushed, the user expects the agent to review the PR (checking diffs, file changes, and correctness) and then squash-merge it into main — all in one directive. The user does not ask for separate review and merge steps; they combine both into a single instruction ('review everything, and if it looks good, squash and merge'). The agent should perform a thorough review first, and only proceed with the squash merge if the review passes. No separate confirmation is needed between review and merge.

<!-- lore:019f1c51-913b-7cdc-8774-2ef7f3d5cd8e -->
* **Always scope new features to the \`packages/opentower\` package**: When adding new functionality (e.g., allowlist filtering, MCP endpoint), the user consistently expects all implementation to live within the \`packages/opentower\` package. The user explicitly states this requirement and expects the assistant to reuse existing patterns within that package (e.g., \`safeTokenCompare\` for auth, \`evaluateAndDispatch\` for dispatch, \`makePipeline\` for sessions). Never suggest creating a new package or placing feature code outside \`packages/opentower\` unless the user explicitly requests it.

<!-- lore:019f1c6b-3334-7163-aafc-51bc4d134cbc -->
* **Always use conventional commits with scope when committing changes**: The user consistently formats git commit messages using conventional commits with a scope, e.g., \`feat(opentower): add MCP endpoint and repository allowlist\`. When preparing commits, follow this format: \`\<type>(\<scope>): \<short description>\` where scope is typically the package or feature area (e.g., \`opentower\`). Common types include \`feat\`, \`fix\`, \`chore\`, \`refactor\`, \`docs\`. The description should be concise and imperative. This applies to all commits in this repository.

<!-- lore:019e148f-265a-741e-8cd4-2ec994a972b4 -->
* **Keep Dockerfile comments concise and why-focused**: Dockerfile comments should be brief (1–2 lines) and explain \*why\*, not restate obvious steps. Avoid multi-line explanatory blocks unless the behavior is non-obvious. Match existing style: short stage headers and minimal inline notes; trim verbose AI-style comments during cleanup.

* **Never create or delete cron jobs without explicit user confirmation**: Cron jobs must never be created or deleted without explicit user confirmation. This is an absolute directive. Always present the proposed job (name, expression, prompt) and wait for approval before calling \`create\_cron\_job\` or \`delete\_cron\_job\`. Applies to agent tools and any automated flow.

<!-- lore:019f1c45-09b4-7b6c-a5e4-fc41c8dbe9ce -->
* **Prefer reading existing config and docs before changing behavior**: The user consistently wants the assistant to inspect the repository’s current structure, config, and documentation first, then explain or plan changes based on what is already there. This applies when they ask about endpoints, deployment, triggers, or setup behavior. They expect the assistant to identify the relevant files, summarize the current implementation, and only then propose a concrete plan or update. Follow this by prioritizing repo discovery, config normalization details, and existing docs over assumptions or immediate edits.

<!-- lore:019f14c7-589e-7f69-abba-dc215b32ae1e -->
* **Prefer repository-specific inspection before making docs changes**: When the user asks for documentation or template files (e.g. OVERVIEW.md, README additions, Railway template overviews), first inspect the existing repo structure, Dockerfile, entrypoints, workflow YAML, and deployment-facing config files. Write the new doc grounded in actual current setup — not generic boilerplate. Prefer concise, accurate docs that reflect how the template really deploys and runs. This applies especially to Railway/template overviews and deployment-facing docs.

* **triggers\[].action must always be null**: In opentower.config.json, \`triggers\[].action\` must always be set to \`null\`. This is an absolute directive — do not set it to any other value.
